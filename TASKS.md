## Track A — Fix Mobile Tab Dual-Animation Ripple (Issue 1)

**Problem:** On the school dashboard (both owner and teacher), when switching tabs on mobile, the `AnimatedContainer` in `_UnifiedMobileTabBar._buildTab` animates BOTH the previously selected tab (fading out background + shadow) AND the newly selected tab (fading in) simultaneously over 180ms. This creates a visible "ripple" on two tabs instead of one clean transition.

**Root cause:** Each tab is an independent `AnimatedContainer` whose `color` and `boxShadow` properties transition when `selectedIndex` changes. When the parent rebuilds with a new `selectedIndex`, every tab widget rebuilds — the old selected tab animates its background from `cs.surface` → `transparent` while the new selected tab animates from `transparent` → `cs.surface`. Both animations run in parallel, creating the dual-ripple effect.

**Fix approach:** Replace the custom `GestureDetector` + `AnimatedContainer` per-tab approach with Flutter's `TabBar` widget connected to the existing `_tabController`. The `TabBar` uses a single sliding indicator that moves between tabs — only one visual element animates, eliminating the dual-ripple. This matches how `_PillTabStrip` (lines 1409-1474) already works for the rail/sidebar layout.

## Track B — Permission-Gated Dashboard Tabs for Teachers (Issue 2)

**Problem:** Teacher dashboard tabs are always the same 4 core tabs (Overview, Academics, Exams, Timetable) regardless of the permissions assigned via roles. Additional tabs like Members, Finance, Attendance, Announcements, and Roles should appear when the teacher's roles grant the relevant permissions. Furthermore, inside the Members page, sub-tabs (Departments, Owners, Teachers, Staff, Students, Guardians) should only show tabs the user has permission to see.

**Root cause:** In `_SchoolDashboardScreenState._initializeSession()` (lines 108-121), permissions are parsed using inline `jsonDecode(r.permissions)` + `Permissions.fromJson(decoded)` wrapped in a silent `catch (_) {}`. If the permission string is in any format that `jsonDecode` or `Permissions.fromJson` can't handle (e.g. the seeder's binary-int-array format `[5,2,0,7,2,0,...]`, or a base64-encoded string from the delta writer), the catch block silently swallows the error. The result: `aggregated` stays as `Permissions.empty()`, `SchoolPermissions` has no permissions, and all conditional tabs in `_itemsForRole()` are skipped.

The resilient `parsePermissions()` function in `_role_helpers.dart` handles ALL known formats (standard JSON, binary-int arrays, base64) and was written as part of BUG-012's fix — but `_initializeSession()` doesn't use it. It has its own fragile inline parsing.

The Members page sub-tabs (`MembersPage.initState()` at lines 82-108 of `members_page.dart`) already correctly filter tabs by permission. Once the permission loading is fixed in `_initializeSession()`, the sub-tabs will automatically filter correctly.

## Track C — Fix Role Edit Permission Persistence (Issue 3)

**Problem:** When editing permissions on an existing role (via the role detail screen's Permissions tab), toggling permissions and clicking Save shows the "Permissions saved." snackbar, but the changes do not actually persist — re-entering the role shows the old permissions.

**Context:** BUG-011 fixed the same symptom for the role CREATE flow by adding a `ValueKey('perms_${role.id}_${role.updated}')` to force fresh state after save. The edit flow uses the same `_PermissionsTab` widget with the same `ValueKey` fix, but the user reports edits still don't persist.

**Likely root causes (to be confirmed via logging):**
1. The `_save()` method calls `serialisePermissions(cleaned)` on the `_editPermissions` map, but `_editPermissions` may have been unexpectedly reset before save (e.g. by a `didUpdateWidget` → `_resetFromRole` call triggered by a concurrent stream emission).
2. The `dao.updateRole()` call may silently fail or update 0 rows.
3. After save, the `ValueKey` may not change if `role.updated` is identical (e.g. same-second save).
4. The `parsePermissions` call in `_resetFromRole` (when the new state is created) may fail on the freshly-saved data.
