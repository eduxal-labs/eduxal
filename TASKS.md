### Task A1: `SystemSettingsScreen` grants Super permissions to all System users

**Files to modify:** `lib/ui/screens/system/settings/system_settings_screen.dart`
**Context files to read:** `lib/ui/screens/system/CONTEXT.md`
**Depends on:** None
**Parallel group:** P1

**Specification:**

The standalone `SystemSettingsScreen` (pushed from the app bar gear icon / user menu) constructs permissions by checking if the user is System OR Super, and gives **both** levels `SystemPermissions.superUser()`. This completely bypasses the RBAC model — any System user gains full unrestricted access to Plans and Subjects management.

The offending code (approximately lines 78–84):

```dart
final permissions =
    (user != null &&
        (user.user.level == UserLevel.super_ ||
            user.user.level == UserLevel.system))
    ? SystemPermissions.superUser()
    : SystemPermissions.none();
```

**Fix:**
Replace the shortcut with proper permission loading. The `SystemDashboardScreen._loadPermissions()` pattern already exists — reuse that approach:

1. Accept `SystemPermissions` as a **required constructor parameter** on `SystemSettingsScreen`.
2. At the call site (in `system_dashboard_screen.dart` where the gear icon / user menu navigates to `SystemSettingsScreen`), pass the already-loaded `_permissions` object.
3. Remove the inline permission computation entirely.
4. If a second call site exists that cannot provide pre-loaded permissions, load them from `SchoolScopesDao` the same way `SystemDashboardScreen._loadPermissions()` does, wrapping the screen in a `FutureBuilder`.

Only `UserLevel.super_` should receive `SystemPermissions.superUser()`. System users get their actual scoped permissions.

### Task A2: `_canGradeContent` — `grades.read` grants grade WRITE access ✅

**Files to modify:** `lib/ui/screens/school_dashboard/academics/paper_detail_page.dart`
**Context files to read:** `lib/ui/screens/school_dashboard/CONTEXT.md`
**Depends on:** None
**Parallel group:** P1

**Specification:**

The `_canGradeContent` getter (which gates all grade entry, answer sheet submission, and AI marking) returns `true` if the user has `grades.read` OR `grades.mark`. Per AGENT.md §17a, `Action.read` means "View records" — it should NEVER allow data mutation. Any user with only `grades.read` can enter scores in the spreadsheet, upload answer sheets, and trigger AI marking.

The offending code (approximately line 175–179):

```dart
bool get _canGradeContent {
  final perms = widget.schoolContext.permissions;
  if (perms.can(Resource.grades, Action.read) ||
      perms.can(Resource.grades, Action.mark))
    return true;
```

**Fix:**
1. Remove `perms.can(Resource.grades, Action.read)` from the condition.
2. Keep only `perms.can(Resource.grades, Action.mark)` as the permission gate.
3. The teacher-specific fallback below (exam creator / invigilator / subject teacher check) already provides correct implicit grading access for teachers — leave that logic untouched.
4. Add an OwnerEntry bypass: `if (widget.schoolContext.currentEntry.value is OwnerEntry) return true;` — this aligns with the existing bypass in `ExamGroupDetailView._canMarkGrades`.

Final shape:

```dart
bool get _canGradeContent {
  if (widget.schoolContext.currentEntry.value is OwnerEntry) return true;
  final perms = widget.schoolContext.permissions;
  if (perms.can(Resource.grades, Action.mark)) return true;
  // ... existing teacher fallback (exam creator / invigilator / subject teacher)
}
```

### Task A3: Role creation/editing allows granting permissions the creator doesn't hold (privilege escalation)

**Files to modify:** `lib/ui/screens/system/roles/create_role_sheet.dart`, `lib/ui/screens/system/roles/role_detail_screen.dart`, `lib/ui/screens/school_dashboard/roles/school_roles_screen.dart`, `lib/ui/screens/school_dashboard/roles/school_role_detail_screen.dart`
**Context files to read:** `lib/ui/screens/system/CONTEXT.md`, `lib/ui/screens/school_dashboard/CONTEXT.md`
**Depends on:** None
**Parallel group:** P1

**Specification:**

When a System user creates or edits a role, the permission checkboxes are not filtered against the user's own permissions. A System user with only `Roles.Create` + `Users.Read` can create a role granting ALL 19 resources × 9 actions, assign it to themselves, and escalate privileges.

This affects 4 files:
1. **System create** (`create_role_sheet.dart`): `_submit()` serialises whatever was checked — no validation.
2. **System edit** (`role_detail_screen.dart`): `_PermissionsTabState._save()` — same issue.
3. **School create** (`school_roles_screen.dart`): `_RoleFormSheet._save()` — same issue.
4. **School edit** (`school_role_detail_screen.dart`): `_PermissionsTabState._save()` — same issue.

**Fix — two-pronged approach:**

**A) UI: Disable toggles the user doesn't hold (all 4 files).**
Each permission editor widget already iterates `kResourceGroups`. For each `ResourceGroup.actions` list, disable (grey out) any action toggle where the editor's own permissions do NOT include that `(resource, action)` pair:
- Each widget already has access to permissions (via constructor parameters or `widget.permissions`).
- For Super users, all toggles remain enabled (Super bypasses everything).
- Pass `editorPermissions` to the permission grid builder and use it to set `enabled: false` on individual `Checkbox` / `FilterChip` widgets.

**B) Save: Validate subset before writing (all 4 files).**
Before the DAO call in each `_save()` / `_submit()`, verify the resulting permission map is a subset of the editor's own permissions. For each `(resource, actions)` in the new map, assert `(newActions & ~editorActions) == 0`. If not a subset, show a snackbar error and abort save. Super users skip this check.
